# ASAP 实施规划与交付

把实施目标转成有责任人、依赖、交付物和验收证据的行动计划。默认中文输出，沿用项目现有术语、编号和文档格式。

## 方法边界

采用经典五阶段：项目准备 → 业务蓝图 → 实现 → 最终准备 → 上线与支持。阶段内允许迭代、并行工作流和分批上线，不把阶段画成机械串行的全部任务。

这是基于 ASAP 的实务裁剪，不是 SAP 官方认证模板。ASAP 存在版本差异；用户指定 ASAP 8 等版本时先核实其路线图。SAP Activate 是其后继方法：遇到 S/4HANA 或云项目，说明适用性差异并尊重用户的既有选择，不混用两套阶段名称。涉及当前产品功能、版本支持或工具选型时另查官方资料，不把旧资料中的工具当作今天的强制依赖。来源见 [方法依据](references/sources.md)。

## 先确定本次交付

从用户材料和已有项目记录中提取：业务目标及成功指标、产品与部署方式、组织及业务范围、当前阶段、目标上线窗口、人员与资源、外部依赖、已批准基线、现有证据。

只追问会改变当前结论的缺项，优先最多三个问题。资料不足仍可输出标明假设的草案；不能虚构预算、人员承诺、已完成工作或签字。区分“事实、假设、待决事项”。没有起始日期时采用相对周次；工期用估算区间并注明依据，不能自动套固定阶段比例。

按用户任务选输出，不每次生成全套材料：

- **启动/总体规划**：目标与范围、五阶段里程碑、工作包、资源与依赖、主要风险、当前阶段下一步。读 [交付模板](references/delivery-templates.md)。
- **业务蓝图**：端到端流程、业务规则及例外、组织/数据/接口、标准能力与差异、验收场景；不止列功能。读交付模板。
- **阶段审查/项目诊断**：对照 [阶段检查](references/phase-gates.md)，列证据、缺口、影响、责任人和关闭条件。
- **变更/延期恢复**：追踪受影响的基线、流程、数据、测试、培训、里程碑和资源；给出保日期、保范围等可行选项的代价及推荐方案。未获批准的变更标为提案，不悄悄重设基线。
- **上线/交接**：检查切换演练、业务准备度、回退或恢复路径、支持接管和稳定期退出条件。读阶段检查和交付模板。

## 执行规则

1. 建立业务需求 → 蓝图决策 → 配置/开发/数据工作包 → 测试案例 → 验收证据的追踪关系。复用既有 ID；新增范围才新增记录。
2. 每个工作包写清产出、执行责任、验收责任、前置依赖、估算和完成定义。未知负责人标“待指定”，建议角色不等于已任命人员。跨模块接口、数据、权限、测试、培训、组织变革与运维作为贯穿工作流，不留到上线前临时补。
3. 排期检查资源冲突、外部交付、数据清洗、业务关键用户和环境可用性。依赖不全时仅标可能的关键路径，不声称已完成关键路径计算。
4. 阶段判定以证据为准。分别给出“通过 / 有条件通过 / 不通过 / 证据不足”的建议与依据；风险接受、正式签字和上线决定属于项目授权角色。会议召开、文档存在、代码完成不等于业务验收。
5. 条件通过必须注明遗留事项、业务影响、责任人、期限及风险接受人；涉及关键业务无法运行、关键数据不一致或无可用恢复路径的缺口，应建议阻止上线。严重级别及阈值按项目约定，不编造 SAP 通用硬指标。
6. 小项目可合并文档及角色，保留范围、验收证据、数据责任和上线决策。用户只要一个文档或一次分析时，就完成该范围，不扩成完整实施工程。
7. 维护已有材料时保留原基线，说明变更和影响。方案编制不等于实际生产操作授权，不把“建议上线”写成“已上线”。

## 输出前检查

先给当前判断或交付结果，再给可执行的表格/说明，最后列最少的待决事项。检查：是否能看出谁做什么、依赖什么、何时完成、谁凭什么验收；是否把推测误当事实；是否遗漏跨流程和跨团队依赖；建议是否与用户当前范围相符。
